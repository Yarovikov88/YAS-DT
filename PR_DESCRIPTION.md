# YAS Digital Twin v2.2 — Семантический граф знаний + сферы HPI

> Закрывает архитектурные замечания v1.0 ревью и формирует основу для HPI-дашбордов.

## TL;DR

**Было (main, v1.0):**
- ❌ Связи как плоский `relations: number[]` внутри строк таблицы `facts`
- ❌ Категория = свалка из контекстов и типов знания
- ❌ Никакого UI

**Стало (v2.2):**
- ✅ Нормализованная схема: `facts` (узлы) + `fact_relations` (рёбра) с типами связей
- ✅ Таксономия HPI: сфера (1 на факт) + теги (массив, контролируемые словари)
- ✅ Интерактивный SVG-граф в Next.js с физикой в Web Worker, готов до 1000 узлов

## Изменения по слоям

### База данных
- `facts.sphere` (TEXT) — одна из 8 сфер HPI: `loved`, `family`, `friends`, `career`, `physical`, `mental`, `hobby`, `wealth`
- `facts.tags` (TEXT[] + GIN) — массив тегов из контролируемых словарей: тип знания, контекст, этап
- `fact_relations` — отдельная таблица рёбер с `relation_type` (10 типов: `causes`, `influences`, `supports`, `prerequisite_for`, `applies_to` и т.д.)
- Каскадное удаление при дропе узла

### Скрипты
- `scripts/migrate-v2.ts` — двухпроходный парсер: дедупликация по title, разрешение коллизий ID, инференс типа связи по содержимому, атомарная заливка
- `scripts/classify-facts.ts` — авто-классификация 196 фактов через Gemini Flash Lite, бэкап в `data/classifications.json`
- `scripts/schema.sql`, `scripts/add-spheres-tags.sql` — DDL для Supabase

### API (Next.js 14 App Router)
- `GET /api/facts` — фильтры по категории/секции
- `GET /api/graph` — `{ nodes, edges, stats }` для рендера; узлы включают `sphere`, `tags`, `content`

### UI
- **Граф**: SVG, force-directed раскладка, цвета по сферам HPI, лейблы с paint-order stroke
- **Производительность**: Web Worker для физики (не блокирует UI), pan/zoom через ref + DOM (без React-ререндеров), hover через CSS `:hover`
- **Управление**: поиск, фильтр по сфере и тегу, кнопки масштаба + ползунок + fit-to-screen
- **Панель деталей**: бейдж сферы, кликабельные `#теги`, markdown-рендеринг контента факта, навигация по связям

## Что **сознательно сделано иначе** чем в ревью

1. **Метрики HPI (`energy_cost`, `voltage_generation`) не на узле.** Один факт может влиять на несколько сфер, поэтому их место — в отдельной таблице `fact_sphere_impact` (это следующая итерация, не входит в этот PR). Класть на узел — терять размерность.

2. **Тип связи по умолчанию не `INFLUENCES`, а инферится.** В `migrate-v2.ts` функция `inferRelationType()` выбирает один из 10 типов на основе содержимого источника. Если контент содержит "основа/фундамент" → `prerequisite_for`, "влия" → `influences`, и т.д. Сводить всё к одному типу — терять семантику, ради которой всё и затевалось.

3. **Сферы вместо `category`.** Старая `category` смешивала типы знания (Принцип, Кейс, Философия) и контексты (Военный, ИТ, Юридический). Разделили: сфера = жизненная область HPI, теги = тип + контекст + этап. Это даёт правильную ось для фильтрации и будущего HPI-импакта.
